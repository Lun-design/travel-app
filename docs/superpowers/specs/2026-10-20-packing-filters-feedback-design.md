# Phase C：打包清單篩選與重複新增回饋

狀態：使用者已確認，實作及本機驗證完成（898 項測試、型別、build、verify:build）；尚未提交／部署，待實機驗收。

## 目標與邊界

完成 UX-04、UX-06。保留既有分類新增、範本匯入、AI 建議、頭像指派、共用勾選、離線與同步。無 DB schema 或完成狀態語義變更，不做 UX-05 每人成員獨立確認。

## 已確認的現況

- `PackingPanel` 的分類列只更新新增項目的 category，但清單依然列出全部分類，容易被誤認為篩選列。
- 新增遇到重複名稱時清空輸入並靜默返回，使用者不知道發生什麼事。
- 已有 userId、assigned_to、assigned_to_all、is_checked 及既有去重工具，可在本地衍生篩選，不需要新增 API。

## 方案比較與建議

1. **建議：獨立檢視篩選。** 新增列保留分類選單；另設清楚標示的檢視條件。資料來源不變，最少影響既有操作。
2. 分類列同時控制新增與檢視：操作少一步，但繼續混淆兩種目的，不採用。
3. 篩選條件交由後端查詢：增加請求、快取及離線複雜度，本階段不需要。

## 操作規則

- 新增列的分類選單僅決定新項目類別，切換檢視不改動它。
- 檢視提供三組可組合條件：分類（全部／既有六分類）、完成狀態（全部／未完成）、指派（全部／我的項目）。
- 「我的項目」包含 assigned_to 為登入者及 assigned_to_all 為 true 的項目；不包含未指派或僅指派給別人的項目。沒有有效登入者時不將 anonymous 當成真實成員。
- 預設顯示全部。切換行程／帳號重設檢視條件；同一行程重新載入維持條件。
- 頂部準備進度永遠依完整清單計算，篩選不會讓整趟行程的完成度跳動。
- 沒有項目與篩選無結果使用不同提示；篩選無結果提供「清除篩選」。
- 重複新增沿用 packingItemKey，維持分類、空白、大小寫與護照同義名稱規則；不擴大去重範圍。
- 重複時不清空輸入、不發送建立請求；提示「此項目已存在」。重設檢視為全部、展開所屬分類並高亮原項目，讓使用者可直接找到。
- 高亮屬於暫時 UI 狀態，不改變項目勾選／負責人；計時器須在卸載及 scope 變更時清理。
- 提交入口加同步鎖，防止同一新增尚未結束時透過鍵盤與按鈕連續送出；不改離線佇列格式與重播規則。
- 新增完成後補載完整清單，避免使舊讀取失效後遺失既有項目；讀取成功仍須保留該帳號／行程待同步的新增、勾選與刪除結果，不能用遠端舊資料覆蓋本機快取。

## 測試與驗收

先補失敗測試，再做最小實作：

1. 三種條件組合結果正確，切換檢視不寫 DB、不改新增分類。
2. 我的項目包括所有人、不包括其他成員及未指派；空清單不崩潰。
3. 篩選後勾選／指派／刪除仍操作正確項目，完整進度不受篩選影響。
4. 父層刷新維持條件；切換行程／帳號不沿用舊篩選或高亮。
5. 同名、大小寫、空白及護照別名重複新增皆無建立請求，保留輸入且顯示既有項目；合法新項目正常新增。
6. 快速連續新增僅發一次建立請求；失敗解除鎖並可重試。
7. 全量執行 npm test -- --run、npm run type-check；正式版 build 及 verify:build 通過才交付。
